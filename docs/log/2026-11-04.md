## F2 bootstate promotion implementation — 2026-11-04

Implemented the first firmware write on branch `firmware/f2-bootstate`. The new
path adds ATA PIO write and cache flush, a board write gate that stays closed
until the self-test and journal check pass, the firmware-side bootstate parser
and `TRYING`→`GOOD` promoter, an in-place `hfs_catalog_overwrite_file` through

The image build now takes `VERSION` and `BOOTSTATE_STATE=trying|good`.
`make -C firmware BOARD=6g VERSION=2 BOOTSTATE_STATE=trying image` produces a
75,520-byte F2 image (`f74e3485…`) with a `TRYING` sequence-1 bootstate.

Host evidence:

- ten firmware host groups, including `test_bootstate`, sanitizer-clean;
- `test_catalog_write` covers in-place overwrite and modify dates;
- `tests/image/f2-test` promotes the TRYING slot through the real writer, runs
  `fsck_hfs`, verifies the manifest/image are unchanged and asks the loader host
  core to select GOOD;
- `tools/check-f2-artifact.sh` does the same for the exact generated F2
  artifact: loader `DEFAULT` before, `promoted sequence 2`, clean `fsck_hfs`,
  loader `GOOD` after;
- the crash matrix adds an overwrite scenario and passes 22 write cuts plus
  flush and partial-sector modes, with every recovered image fsck-clean.

The first F2 device attempt stopped at the loader's
`Executing signed test payload...` line and blanked the screen. The F2 image's
601 KB BSS started at `0x08800000` and zeroed the loader test image's BSS,
framebuffer and LCD DMA scratch (`_end` `0x08884200`). F1's 229 KB BSS had
stopped below the active LCD DMA buffers. The F2 BSS now starts at
`0x08890000`, the range `0x08800000`–`0x0888ffff` is reserved, and the linker
asserts `__bss_start >= 0x08890000`.

The next device attempt reached F2 but failed in the PMU stage with `-1`. The
step-by-step PMU probe reported `STAGE 49`, which is the advisory
interrupt-latch clear after all 48 preinit registers succeeded. `helikon_pmu_init`
treated a failed latch read as fatal. That block is now best-effort: the mask is
already set to `0xff`, and a failed latch read no longer blocks the version
check or backlight init.

The next run reached F2 and failed at `ATA` with `-1`. The new F2 step
`SET FEATURES 0x02` (enable volatile write cache) is rejected by this iFlash
SD bridge even though reads, writes and flush work. It is now best-effort:
the firmware records whether the cache was enabled, ignores a rejected hint,
and still requires a successful flush before a journal commit. The rebuilt F2
image is 75,520 bytes, SHA-256 `f74e3485…`.

The next run passed PMU/LCD but still failed at ATA `-1`. The loader had already
powered the disk to read the image, so the redundant PMU HDD-enable write is now
best-effort; the controller reset and identify decide whether storage is
available.

The ATA step probe reported `HDD 0`, first and second stage 2, `IDENTIFY -1`,
and all ID words zero. The disk was powered, but the controller reset left the
iFlash SD bridge unable to answer IDENTIFY. F2 now tries a warm IDENTIFY on the
loader's already-configured ATA controller first, and only falls back to the
full reset path if that fails. The F2 image is 75,520 bytes, SHA-256
`f74e3485…`.

The ATA probe still showed `IDENTIFY -1` on the warm and full-reset attempts,
so the handoff boundary was fixed: the loader test image now builds with ATA
DMA disabled and leaves the controller active before the jump, so F2 does not
have to recover a DMA session. The loader build is `8f80e40d…` (106,088
bytes), host-verified, not device-tested.

The ATA probe still failed IDENTIFY. Code comparison against the donor found
the driver bug: our `ata_identify()` waited for `DRDY` before the command and
for an end-of-transfer status afterward. The donor waits only for `!BSY`,
issues IDENTIFY, waits for DRQ, reads the 256-word table, and does not require
a post-transfer end status. This iFlash SD bridge does not assert DRDY in the
handoff state. The firmware now matches the donor sequence. The F2 image is
75,520 bytes, SHA-256 `f74e3485…`.

The next device run with the PIO-only loader and the donor IDENTIFY sequence
still stopped at `ATA error -1`. The loader had just read the whole image over
the same controller, so the bridge is not dead: the failing operation is the
second IDENTIFY. F2 now adopts the loader's live controller with a
before-reset sector-0 read, keeps the HDD rail powered by not clearing AUTOENA
in PMU preinit, and falls back to the donor reset only on cold boot. The first
adopt probe read `RDY 0 CSD 0 DAD 0`, the signature of a loader that ran
`ata_sleepnow`: ATA_CONTROL was off and the HDD rail was down. Adopt now reads
AUTOENA, powers the rail and waits 2 s, then re-enables `ATA_CONTROL` and PIO
timing without the reset or IDENTIFY. The next probe showed `CTL 1 PWR 1 RDY
0`: the rail was on, but a soft enable did not raise PIO ready. A controller
reset does (stage 1 passes), so adopt now has a second phase that runs the
donor reset without IDENTIFY and reads sector 0. The normal image is 76,160
bytes, SHA-256 `f33f2791…`; the adopt probe is 77,136 bytes, SHA-256
`beec14c2…`. No device result yet.

No successful F2 device run and no device power-cut run. The runbook is
[`../f2-bootstate-test.md`](../f2-bootstate-test.md).
