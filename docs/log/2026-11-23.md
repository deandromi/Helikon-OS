# 2026-11-23

## Catalog operation property test (T-136) and the staging fix it found (T-135)

The journal, the bitmap and the transaction overlay each have a property test;
the catalog writer had only its hand-written cases. `tests/hfsplus/test_catalog_ops_props.c`
closes that: a random sequence of creates, deletes, renames, writes and
truncates on a 1 MiB volume with 4096-byte nodes, and after every operation the
whole world is checked against a directory model — every folder's children by
name, ID and kind, every folder's valence against its child count, every file's
size and contents read back through the reader, the volume header's file and
folder counts, and `hfs_check_volume`, which re-walks the catalog and extents
trees and compares every fork against the allocation bitmap.

The model is written from the documentation: deleting a folder with children is
`NOT_EMPTY`, moving a folder into its own subtree is `ARGUMENT`, truncating past
the end is `ARGUMENT`, and a refused call must leave the image byte-identical.
The fixture is 4096-byte nodes on 512-byte blocks, which is what makes several
file records share a leaf, so inserts split nodes and deletes merge them instead
of every record owning a node of its own.

**The fixture caught two mistakes in itself first.** Its catalog header claimed a
maximum key length of 520, and `hfs_btree_open` refuses anything above node size
plus four — the existing writer tests never open the tree through that path, so
nothing had noticed. And its volume header counted the root folder, while a fresh
`newfs_hfs` volume says 0 files and 0 folders: the check excludes parent ID 1,
and it is right to. Both are fixture bugs, both were confirmed before changing
anything (the second by creating a 10 MiB HFS+ image and reading the header).

**Then it found a real one (issue #115).** With 512-byte allocation blocks, every
B-tree node cost one transaction slot per sector, so a root split — four nodes
plus the two volume-header copies — needed 34 slots of 32, and the catalog could
never grow past depth 1. The image was never corrupted, because a refused
transaction is simply not applied, but the refusal was permanent. Raising
`HFS_TXN_MAX_BLOCKS` to 96 made the same sweep pass, which isolated the budget.

`hfs_txn_stage_replace` now means "these bytes shall hold this data": the exact
range is replaced, a range inside or overlapping a staged run is merged into it
while the union fits in `HFS_TXN_BLOCK_MAX`, and a union that would not fit is
refused with `BUSY` without changing anything. Runs that merely touch stay
separate entries — neighbours are different objects. `hfs_fork_stage_map` stages
runs of whole allocation blocks, so a node is one entry and a root split six.
The journal was already able to write an entry of any sector-multiple size, so it
needed no change.

**Tests updated with the contract.** `test_txn.c` gained explicit cases for the
patch, the overlap growth, adjacent runs staying separate and the over-limit
refusal. `test_txn_overlay_props.c` was rewritten around a byte map: it
cross-checks the map against the transaction's own entries after every step, so
a merge that moved a byte would be caught at once, and it predicts only the union
size from the entries, because a byte map cannot tell two abutting entries from
one run.

**Evidence.** 600 operations (90 creates, 66 deletes, 102 renames, 93 writes, 32
truncates) in the committed sweep, plus 1,200 operations over a second seed;
`make -C tests/hfsplus test` and `sanitize` exit 0; `./tools/host-tests.sh clang`
passes 9 suites and `--sanitize` 8; `./tools/static-analysis.sh` reports nothing;
the 6G cross-build is 80,840 bytes. Host-only: no device run, and the F2 write
path stays unconfirmed.

## Node ownership in the structural check (T-137)

**The gap was the one every writer bug hides in.** `hfs_check_volume` walked each
tree's leaf chain, checked key order across leaf boundaries, validated every
catalog record body and followed every index node's child pointer — but it never
looked at the free-node map. A node the tree can no longer reach but the map
still marks used is a block gone for good: `fsck_hfs` counts the free nodes in
that map, so the volume's free space disagrees with itself forever. The other
direction is worse. A node the tree *does* reach but the map marks free is a node
the next split will overwrite, records and all.

`check_tree_nodes()` closes both. It opens the tree, reads node 0 through
`hfs_fork_read` — not `hfs_btree_read_node`, which refuses an `empty` tree — and
copies the map record out. It marks the header node used, then walks every node
reachable from `root_node` through the index child pointers, marking as it goes.
Two comparisons follow: used-and-reachable against unused-and-unreachable for
every node in `total_nodes`, and the map's clear-bit count against the header's
own `freeNodes`. Catalog, extents and attributes trees each get the pass when they
have nodes. It is bounded rather than clever: past 16,384 nodes or a 512-deep
walk it records `HFS_CHECK_SKIPPED_NODES` and says nothing about that tree, for
the same reason a large volume's bitmap is reported "not checked" instead of
corrupt.

**Teeth first, then trust.** Dropping `map_set(header, node, 0)` from
`hfs_btree_free_node` makes the catalog model test stop at step 95 with
`problems 0x00080000` — the exact failure a real leak would produce. That
mutation also cost an hour of confusion: the model test then kept failing after
the source was restored, because the binary under `tests/hfsplus` was the
mutated build. `make clean` and a rebuild pass at 600 steps and at 700 steps over
six seeds, plain and under ASan/UBSan. **If a suite ever fails only sometimes,
delete the binary before believing it.**

`test_check` gains three cases on a hand-built volume: a node marked used that the
tree cannot reach, a reachable node cleared to free, and a header free count that
disagrees with the map. 29 cases now, all passing. Host-only; no device run and
no change to the F2 write path.

## A model test for the tree itself, and the growth limit it found (T-138, T-139)

**The catalog test checks the catalog; nothing checked the tree.** `test_btree_model`
drives the extents-overflow tree directly: random inserts, deletes and in-place
updates, 512-byte nodes in a 1 MiB volume, about six records per leaf. After every
operation it compares `find` against a sorted model, walks the leaf chain and
requires it to be exactly the model with strictly ascending keys, and runs
`hfs_check_volume` — which now includes node ownership. A refused call has to
leave the image byte-identical.

**It found a growth limit (issue #118).** With a map record sized for exactly the
nodes the tree had, the first insert past the last node answered `-4`
(`HFS_ERR_UNSUPPORTED`) at step 1386. `grow_locked()` refused when
`total_nodes == map_length * 8`, but the map record sits at the front of the
header node with the node's free space right behind it: growing the map by two
bytes — and moving the free-space offset table entry with it — is all a tight map
needs. macOS never hits this because it sizes the map to fill the header node at
format time (a 20 MiB `newfs_hfs` volume: `totalNodes` 40, map record 3840 bytes =
30,720 bits), but any other formatter can produce a tight one, and our own
eventual formatter will.

The same code path reported two ordinary capacity outcomes as `UNSUPPORTED`: a
map that cannot widen, and a fork with no free extent slot. Both now answer
`HFS_ERR_NO_SPACE`, which is what a caller can act on. `fork_offset()` also
learned the attributes fork (352), so that tree can grow at all.

**Two mistakes in the test, kept in the record.** The model array was 512 entries
and a long sweep reached 513, scribbling over the neighbouring data and producing
a phantom "record body differs" at step 2551 — the kind of failure that looks like
a firmware bug for an hour. It is 1,024 entries with a guard now. And the first
version of the model dump printed the key area as zeros, which made the two
records look different in the wrong bytes; the fixture dump that finally settled
it came from writing the image and model to files and diffing them in Python.

**Teeth.** Forcing `widen_map()` to refuse fails `test_btree_grow`'s widening
case; restoring `UNSUPPORTED` at either capacity point fails its own case;
dropping `map_set(header, node, 0)` from `free_node` stops the model test at step
54 with `problems 0x00080000`.

**Evidence.** `make -C tests/hfsplus test` 163 cases and `sanitize` exit 0;
`test_btree_grow` 5 cases; the committed 1,800-operation sweep reaches 270 keys at
depth 3 and grows the tree from 64 to 70 nodes; 2,600-operation sweeps over six
seeds reach 513 keys and 128 nodes (the whole fork) and pass. Host-only: no device
run, and the F2 write path stays unconfirmed.

## A mutation sweep for the writer, and the reserved CNID it found (T-140, T-141)

**Readers were swept for crashes; the writer had never been swept for damage.**
`test_writer_mutations` starts from a valid volume the writer can create a file
in, corrupts one structural field — both volume headers, every fork record, the
catalog header node and its first leaf, 33 fields in all, plus a seeded random
tail — and then drives `probe → check → catalog open → create file` inside a
transaction. Two rules, and nothing else: a refused call must leave the image
byte-identical, and a committed write may never turn a volume the check called
clean into an inconsistent one. Mutations whose correct answer is a refusal are
marked as such and must be refused.

**It found issue #120 at seed 12345, iteration 330.** A random 4-byte write
landed on the volume header's `nextCatalogID` and zeroed its low byte. The writer
read the field and used it, inserting a file record under CNID 0 — and with the
field set to 2 it would have written a second record claiming the root folder's
own CNID. Nothing stopped it: `hfs_check_volume` never looked at `nextCatalogID`,
so the volume was reported clean right up to the first create, and the damage only
appeared afterwards as a catalog-body finding.

`create_object()` now answers `HFS_ERR_FORMAT` when `nextCatalogID` is below 3 (0
and 1 are reserved, 2 is the root), when it is `0xffffffff`, and when either
volume count is `0xffffffff`, because the increment would wrap. The
`0xffffffff` case came from the same sweep a few minutes later: with the field
all ones the create committed a header whose next ID had wrapped to zero, and the
check that had called the volume clean now reported it. The check reports the field as
`HFS_CHECK_CATALOG_ID` (0x00200000), so the anti-corruption gate can refuse the
volume before any writer touches it. `test_check` is 30 cases: the new one sets
the field to 2 and expects the finding, and the fixture now writes 16, the value a
formatter leaves.

**Teeth.** Skipping the file-count update in a create fails the sweep's pristine
sanity case immediately (the check reports the count mismatch). Accepting a
reserved CNID fails the curated `next catalog id zero` case with "the write
should have been refused". Removing the check's new bit fails `test_check`.

**Evidence.** The committed sweep is 34 curated + 400 random iterations, and
3,000-iteration runs over seeds 12345, 7, 99 and 555: 411 and 2,971 committed
writes respectively, every clean-before case still clean after the commit
(12 and 33 commits happened on volumes the check already called inconsistent, and
the check still ran). Host-only; no device run.

## CI: a scheduler that does not run, and a job that would not die

**Three things were red or stuck, and only one was the code's fault.**

`preview-2026-11-22` exists because the owner dispatched the workflow by hand.
The dispatch before it had failed: the gate job ran `./tools/host-tests.sh clang`
without Pillow and mutagen, so `tests/musicdb` could not build its HDB fixture
(`hdb_build.py needs mutagen and Pillow`). That was fixed in #103 by installing
`python3-pil python3-mutagen`, and the second dispatch published in three
minutes.

**The nightly has never run.** `preview.yml` has carried `cron: '17 4 * * *'`
since #89, and the Actions API lists exactly two runs, both `workflow_dispatch`.
GitHub's schedule trigger is unreliable for public repositories right now — the
community threads through November 2026 report runs arriving seven to eight
hours late, or not at all — so waiting for the cron is not a plan. The workflow
now also runs on a push to `main`, with a new first job, `check`, that looks up
`preview-<today>` through `gh api` and skips the build when it exists. One
prerelease per calendar day, from whichever trigger gets there first; a manual
dispatch still replaces the day's release, as before.

**A job that would not die.** During the T-140 pull request the `firmware builds`
job sat in `apt-get install gcc-arm-none-eabi` for sixty-five minutes. Nothing in
the workflow bounded that, and a job gets six hours before GitHub kills it, with
the pull request waiting the whole time. Cancelling and re-running it finished in
2m17s. Both workflows now set `timeout-minutes` on every job (20–40 minutes,
five for the lookup) and pass `-o Acquire::Retries=3` to every `apt-get`, so a
flaky mirror fails the job in minutes instead of holding the queue.

Host-only, of course: CI is evidence that the host suites pass and nothing more.

## Four tests, one writer fix, and a gate nobody had pinned (T-142 to T-145)

**The writer could not empty a deep tree (issue #125).** `hfs_btree_delete` handled
a non-root leaf that lost its last record only when its parent was the root or the
grandparent still had children; everything else answered `HFS_ERR_UNSUPPORTED`.
The refusal was clean, but a long drain leaves one-child index nodes behind, so the
last records of a depth-3 tree hit exactly the shapes it refused: the tree could be
filled and then never emptied from the top. That is the state a truncate to zero
extents and a delete of the last file in a folder both reach. `collapse_empty_leaf`
now unlinks the leaf, frees every ancestor left without a child, rewrites the parent
key when the first record went, and ends at either a root that keeps records or the
canonical depth-0 tree. Its first cut returned before `store_header` and the new
test caught it immediately with `leaf_next returned -3`, the chain head still
pointing at the freed leaf.

What found it is the ordered half of the B-tree model test (T-143): after the
random sweep it drains the model in ascending key order — every delete takes the
leftmost leaf's first record, so the parent key is rewritten every step — requires
the canonical empty tree in memory and again after reopening from the medium, fills
120 ascending keys from empty so the root grows out of depth 0, drains again, and
inserts three keys through the reopened handle. Random deletes never reached those
cascades; the ordered ones reach them every time.

**Invariant 4 had only integration coverage (T-142).** "A dirty journal means no
writes" is enforced in `hfs_txn_begin`, the only way a caller obtains a transaction,
and nothing tested it directly: both kinds of dirt — a header whose `start` and `end`
do not meet, and a volume header with the dirty flag — must answer `HFS_ERR_DIRTY`
and leave the transaction inactive, while a clean journal still has to open one, so
a gate that refuses everything cannot pass.

**Names are folded twice as often as the model knew (T-144).** The catalog orders
keys with the case-folded FastUnicodeCompare and stores the case the caller passed,
so the search and the insert have to agree. `test_catalog_ops_props` only generated
uppercase letters and digits, which never asks the question. It now draws mixed-case
names, keeps the model's uniqueness rule case-insensitive (an ASCII fold written from
the format), and after the sweep takes a name the catalog holds, flips its case, and
requires both a create and a rename onto it to answer `BUSY` with the image
untouched. Teeth: swapping the folded comparator for a raw byte comparison fails the
probe at once with `create fIjmjoaC under 68: rc=0, expected BUSY`.

**The write-path sweep never allocated a block (T-145).** Create, rename and delete
take catalog nodes and nothing else, so a corrupted allocation bitmap or fork record
was never reached by a writer. Each iteration now runs five calls — create, rename,
write 1,500 bytes, truncate to zero, delete — each in its own transaction, each held
to "a refused call changes nothing" and "a commit never turns a clean volume
inconsistent". Four seeds and 4,500 iterations found no new defect, which is the
answer it should give: the gate and the writer's bounds checks already covered those
fields, and now the path that touches them proves it.

Host-only, as always: these are host suites, not device runs.

## A catalog that can empty itself, and thread records that finally get checked (T-146, T-147)

**T-146 — the model sweep ends by emptying the catalog.** The random sweep never
ends empty, so the state that deleting the last file in a folder leaves was
untested at the catalog layer. It now drains itself — files first, then folders
with no children — and requires the end state: one leaf deep, exactly the root's
two records, every other node back on the free-node map, no children, the volume
header counting nothing, and the structural check clean. Three fresh creates
follow, because a catalog that drains but cannot be refilled should not pass. What
it does *not* cover is written down in the test: with 4 KiB nodes a leaf is merged
away before it empties, so a leaked node in `collapse_empty_leaf` passes here and
the B-tree model test is what catches it.

**T-147 — the structural check pairs every record with its thread record.** Thread
records are how a CNID resolves back to a name, and nothing checked them. A file
record with no thread is an item no inode lookup can find; a thread carrying the
wrong parent or name is worse, because the lookup succeeds and returns the wrong
file. `hfs_check_volume` now pairs them in both directions through the catalog
itself — a second B-tree handle with its own node buffer, searched by hand because
the check has no transaction — so the pass costs one node buffer and no cap, and a
catalog of any size is checked in full. A table would have needed a skip bit, and
a skip bit on this rule would have skipped every real volume.

The false-positive question is the one that matters, so it was answered against
macOS: a pristine 16 MiB `HFS+J` volume reports clean, and so does the same volume
after the writer's random create/append/truncate/rename/delete run, with
`fsck_hfs` clean on both. `test_check` is 35 cases, five of them new.

Host-only, as always: these are host suites, not device runs.

## Index nodes that finally merge (T-150)

A B-tree delete did three things about space: it merged two under-half leaves, it
moved a record between leaves when a merge did not fit, and it collapsed an emptied
leaf through its ancestors. It never paired two *index* nodes. A one-child index
node is not corrupt — the keys below it are reachable, key order holds, node
ownership is right, `hfs_check_volume` passes — which is why it went unnoticed:
the tree was correct and wasteful at the same time, keeping a level per surviving
child, and those nodes could never be reused.

The model test now asks for the shape directly. `check_occupancy` walks the index
nodes from the root after every operation and rejects any holding fewer than two
records. It failed on the first run of the existing sweep — `step 1000063, index
node 3 at level 1 holds 1 record(s)` — so the gap was real, not a tidy-up.

`settle_index_nodes` runs after an operation takes a record out of an index node.
It pairs the node with its next sibling (or its previous one, when it is the last
child), merges them in key order when the combined records fit, drops the absorbed
node's record from the parent and puts the node back on the free-node map, then
repeats one level up because the parent's record count just changed. When the two
do not fit it moves one child across from the sibling, rewrites the single parent
key that changed, and stops. `collapse_root` takes a level off a root left with
one child, repeatedly, and never enters the empty-tree state — that stays the
delete path's own job.

Two mutations, both caught: disabling the merge fails at the same step with the
same message; disabling only the root collapse fails at `step 1000207` with `index
node 31 at level 0 holds 1 record(s)`. The steal fallback is not reached by any of
the seeds — after a split a node is at most half full, so one child plus a
half-full sibling always fits — and that is recorded rather than glossed over.

Host-only, as always: `test_btree_model` runs on a hand-built fixture, so this is
evidence about the writer's shapes, not about a device.
