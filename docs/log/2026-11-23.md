# 2026-11-23

## Catalog operation property test (T-136) and the staging fix it found (T-135)

The journal, the bitmap and the transaction overlay each have a property test;
the catalog writer had only its hand-written cases. `tests/hfsplus/test_catalog_ops_props.c`
closes that: a random sequence of creates, deletes, renames, writes and
truncates on a 1 MiB volume with 4096-byte nodes, and after every operation the
whole world is checked against a directory model — every folder's children by
name, ID and kind, every folder's valence against its child count, every file's
size and contents read back through the reader, the volume header's file and
folder counts, and `hfs_check_volume`, which re-walks the catalog and extents
trees and compares every fork against the allocation bitmap.

The model is written from the documentation: deleting a folder with children is
`NOT_EMPTY`, moving a folder into its own subtree is `ARGUMENT`, truncating past
the end is `ARGUMENT`, and a refused call must leave the image byte-identical.
The fixture is 4096-byte nodes on 512-byte blocks, which is what makes several
file records share a leaf, so inserts split nodes and deletes merge them instead
of every record owning a node of its own.

**The fixture caught two mistakes in itself first.** Its catalog header claimed a
maximum key length of 520, and `hfs_btree_open` refuses anything above node size
plus four — the existing writer tests never open the tree through that path, so
nothing had noticed. And its volume header counted the root folder, while a fresh
`newfs_hfs` volume says 0 files and 0 folders: the check excludes parent ID 1,
and it is right to. Both are fixture bugs, both were confirmed before changing
anything (the second by creating a 10 MiB HFS+ image and reading the header).

**Then it found a real one (issue #115).** With 512-byte allocation blocks, every
B-tree node cost one transaction slot per sector, so a root split — four nodes
plus the two volume-header copies — needed 34 slots of 32, and the catalog could
never grow past depth 1. The image was never corrupted, because a refused
transaction is simply not applied, but the refusal was permanent. Raising
`HFS_TXN_MAX_BLOCKS` to 96 made the same sweep pass, which isolated the budget.

`hfs_txn_stage_replace` now means "these bytes shall hold this data": the exact
range is replaced, a range inside or overlapping a staged run is merged into it
while the union fits in `HFS_TXN_BLOCK_MAX`, and a union that would not fit is
refused with `BUSY` without changing anything. Runs that merely touch stay
separate entries — neighbours are different objects. `hfs_fork_stage_map` stages
runs of whole allocation blocks, so a node is one entry and a root split six.
The journal was already able to write an entry of any sector-multiple size, so it
needed no change.

**Tests updated with the contract.** `test_txn.c` gained explicit cases for the
patch, the overlap growth, adjacent runs staying separate and the over-limit
refusal. `test_txn_overlay_props.c` was rewritten around a byte map: it
cross-checks the map against the transaction's own entries after every step, so
a merge that moved a byte would be caught at once, and it predicts only the union
size from the entries, because a byte map cannot tell two abutting entries from
one run.

**Evidence.** 600 operations (90 creates, 66 deletes, 102 renames, 93 writes, 32
truncates) in the committed sweep, plus 1,200 operations over a second seed;
`make -C tests/hfsplus test` and `sanitize` exit 0; `./tools/host-tests.sh clang`
passes 9 suites and `--sanitize` 8; `./tools/static-analysis.sh` reports nothing;
the 6G cross-build is 80,840 bytes. Host-only: no device run, and the F2 write
path stays unconfirmed.
