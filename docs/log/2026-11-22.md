# 2026-11-22

## Both halves of Disk Mode have an image

**Goal.** A player can be formatted from a laptop with either the firmware or
the bootloader in charge.

**Firmware.** The Disk Mode image grew a confirmation gate — SELECT hands the
disk over, MENU or 30 s powers off — and a status line with the capacity and
the addressing mode. `helikon_board_storage_init_writable()` in the board gives
Disk Mode a writable block device; `helikon_board_storage_attach()` keeps the
read-only flag for everything else. `disk_mode` restore mode clears the
read-only flag on its private copy itself, and the host test now starts from a
read-only device so that clearing is what the write proves. Image: 40,524 bytes,
no `hfs_volume_probe` symbol.

**Bootloader.** `bootloader/hardware/helikon_usb_disk_hw.c` builds the seam the
firmware stack expects over `ata_read_sectors`/`ata_write_sectors`/`ata_flush`,
`udelay` and `PWRCON`, polls `helikon_usb_irq()` instead of reaching into the
donor VIC, asks for SELECT, and calls `helikon_disk_mode_start()` after
`storage_init()`, before any mount. The entry is `noreturn`, so no path can
fall through into the donor's filesystem code. `donor-usb-disk.patch` adds the
sources and the call; `tools/build-usb-disk-bootloader.sh` exports the donor at
the pinned commit, applies it and writes the image and a DFU file.

**Evidence (host and build only).** Image 108,296 bytes, SHA-256
`de9b67e3…`; DFU 116,432 bytes, SHA-256 `e27d3b38…`; `_moveend 0x2203ae40`
against `MOVE_AREA` end `0x22040000`, 20,736 bytes of headroom; two builds
produced identical hashes; the image contains `helikon_usb_init`,
`helikon_disk_mode_start` and the "Helikon Disk Mode" string. `tests/usb` plain
and under sanitizers passes. Every other host suite passes on the merged tree.

**Not attempted.** No device run for either image. Neither has enumerated,
mounted or been formatted. D-56 (VID/PID) is open, so a host sees the
placeholder identity.

## The clock-gate inversion

Auditing the controller against the donor's `usb-s5l8702.c` turned up one
thing that a mock cannot see: PWRCON bits are power-*down* gates, so enabling a
clock clears the bit. `clock.c`, `pmu.c`, `buttons.c` and `ata.c` all do that;
both USB seams set the bit, which gates the OTG and PHY clocks off before the
core is touched. Fixed in `firmware/hal/6g/usb_target.c` and
`bootloader/hardware/helikon_usb_disk_hw.c`; the audit table and the fixed
values live in `usb-device-stack.md` §11. The Disk Mode image is 40,524 bytes
after the fix, the bootloader image 108,296 bytes (SHA-256 `de9b67e3…`).

## Fuzzing the transport (T-115)

`tests/usb/fuzz_msc` is deterministic: a fixed seed produces the same byte stream
on every host, so a failure reproduces from the printed seed. It drives the real
`usb_msc.c` over a sparse 4 TB fake disk and covers four cases — whole disk,
volume window, read-only device, I/O faults — 162,500 commands per run, and runs
under ASan/UBSan in `make -C tests/usb sanitize`.

What it checks: the CBW is either accepted or refused with `HELIKON_ERR_FORMAT`
and nothing else; the window never moves; no sector outside the window is read
or written; a read-only device takes zero writes; the CSW has the `USBS`
signature, echoes the tag, carries a status byte in range and a residue no
larger than the declared transfer; a failed command leaves a sense key; a device
error is never reported as success; eject only ever comes from START STOP UNIT,
and reading it consumes it.

What it found: a refused CBW used to be dropped silently, with no CSW and no
state, so the host waited out its transfer timeout before resetting the pipe.
`helikon_usb_msc_phase_error_csw()` now builds the 13-byte answer — `USBS`, the
tag echoed from the broken CBW, zero residue, `PHASE_ERROR` — and
`disk_mode.c` sends it before returning to idle. `test_disk_mode` pins that
sequence, including the re-armed CBW afterwards.

Sizes after the change: Disk Mode firmware 40,524 bytes; bootloader image
108,296 bytes, SHA-256 `de9b67e3…`; DFU 116,432 bytes, `e27d3b38…`; `_moveend`
20,736 bytes inside `MOVE_AREA`. Still no device run.

## Replay hardening for the journaled writer (T-018)

The replay contract in `hfsplus-write-engine.md` §10.5 says replay is idempotent
and that the journal is preserved on any replay failure. Both were asserted in
prose and untested in bytes; the crash matrix cut the *transaction*, never the
replay.

`tests/image/hfs_crash_test` gained two modes:

- `replay-twice SCENARIO` — recover the image, close it, open and recover again.
  The second pass must find a clean journal and the identical tree. This is what
  idempotency looks like from outside: a replay that is not idempotent shows up
  as a changed tree or a journal that never goes clean.
- `replay-cut SCENARIO N` — fail the nth write of the replay itself, leaving the
  image half-replayed on purpose. The next recovery must land on one of the two
  legal states (before or after the transaction) and never on a mixture.

`tests/image/run-crash-macos.sh` now runs `replay-twice` at every cut point and
the double fault on a sampled subset (`DOUBLE_CUTS`, `DOUBLE_SCENARIOS`), with
`fsck_hfs -fn` after each, and takes `SCENARIOS="create grow"` to narrow a run
while iterating.

Evidence from the run on this machine (macOS, a 16 MiB `HFS+J` image made by
`hdiutil`): `SCENARIOS="overwrite grow"` covered 118 cut points across the write,
flush and partial matrices — overwrite 21 + 4 + 21, grow 34 + 4 + 34 — and every
one recovered, was idempotent on a second recovery, and came out of
`fsck_hfs -fn` clean. The 16 replay double faults at the first four cut points of
each write matrix all converged on a legal state and were fsck-clean too. Exit 0,
zero failures. No device was involved and nothing was written outside the test's
own temporary images.

## Fuzzing the Disk Mode state machine (T-115)

`tests/usb/fuzz_mode` is the layer above `fuzz_msc`: random control requests,
CBWs of the wrong length, data arriving when no command expects it, completions
nobody asked for, resets and disconnects — 20,000 events per walk in restore and
read-only mode, then a liveness check (after any walk, a bus reset and a fresh
SET_CONFIGURATION, a valid INQUIRY must still be answered). It also runs the
100 connect/disconnect cycles T-115 asks for, on the mock.

What it found: **after the medium was released, the mode still ran commands.**
A host that had not noticed the eject could send one more WRITE(10) and it went
straight to the block device — the volume the rest of the firmware believes it
owns. `handle_cbw()` now refuses anything unless the state is `ENUMERATED`,
counts the packet and stays idle. `test_disk_mode` pins it, including that the
fake disk records no write.

Sizes after the change: Disk Mode image 40,524 bytes; bootloader image 108,296
bytes, SHA-256 `de9b67e3…`; DFU 116,432 bytes, `e27d3b38…`; `_moveend` 20,736
bytes inside `MOVE_AREA`. Normal firmware unchanged at 80,008 bytes. No device
run.

## The >128 GiB format path, tested on the host

`tests/image/run-format-macos.sh` runs the real `tools/disk-mode-format.sh`
against a 140 GiB sparse image. The guards are checked first — a slice passed as
`--device`, a missing backup record, an empty one, and a path that is not a
block device all have to be refused — then `--dry-run` must print its commands
and change nothing, then the real run must produce an APM with one `Apple_HFS`
volume above 137,438,953,472 bytes and `fsck_hfs -fn` must call it clean.

Result on this machine: `/dev/disk4` at 150.3 GB, one `Apple_HFS IPOD` slice of
150,189,596,672 bytes, `fsck_hfs` "The volume IPOD appears to be OK", PASS. The
volume is not left mounted, because macOS writes `.fseventsd` and `.Trashes` on
a first mount and the test would then be describing a volume it had changed.

That is the host half of the owner's 128 GiB goal: the tool, the partition map
and the filesystem. It is not a device result — no iPod was in the loop.

## A read-only structural check (T-020)

`firmware/hfs/hfs_check.c` is the first slice of the anti-corruption work: a
read-only pass that answers whether a volume's metadata agrees with itself. Block
size and count; every fork's extents against the volume; fork sizes against the
blocks they have; the allocation file against the block count; the free-block
count against the bitmap when the whole bitmap is inline; and the catalog,
extents and attributes B-tree headers through the reader's own validation.
Nothing is written and nothing is allocated.

Two design decisions came out of running it against real volumes:

- **The bitmap's padding bits are not a finding.** macOS leaves them zero on a
  freshly formatted volume, so an earlier version flagged every real volume whose
  block count is not a multiple of eight. That is exactly the false alarm a scrub
  must not have; the padding is now ignored and a host test pins it.
- **"Not checked" is not "broken".** A large volume keeps its bitmap in the
  extents overflow tree, which this pass does not chase. `skipped` is a separate
  field from `problems`, so a 140 GiB volume reports clean with a note instead of
  a failure.

Evidence: 13 host cases (`tests/hfsplus/test_check`), one corruption each, clean
volume zero findings. A real 32 MiB `HFS+J` volume: clean, exit 0. The same
volume with `free_blocks` bumped by five: the mismatch is reported, exit 1. A
140 GiB volume formatted by `tools/disk-mode-format.sh`: clean with the bitmap
marked not checked, exit 0. `tools/hfs-check.c` is the host CLI behind those
runs (`make -C tests/image hfs-check`).

### The catalog counts, and two conventions that only real volumes show

The first draft of the catalog walk counted records with a one-byte record type
and treated the root folder as a normal folder. Both are wrong, and both are the
kind of wrong that only shows up against a formatted volume: the record type is a
big-endian 16-bit field after `2 + keyLength`, and the root folder has a catalog
record of its own — parentID 1, named after the volume — that the header's folder
count excludes.

With both fixed, the walk agrees with the header on every volume tried: a 32 MiB
`HFS+J` image reads 2 files and 2 folders (the two journal files and two hidden
folders), the 140 GiB volume from the format test reads 5 and 3 across 14,208
catalog nodes. The numbers are printed by `hfs-check` now, so a future mismatch
can be read instead of guessed at.

## Overflow extents, and the large volume's bitmap

The structural check now reads the allocation file through a resolved extent map:
`hfs_extents_collect` supplies the inline extents plus the records from the
extents overflow tree, in logical order, and a small reader walks that map. The
map, not `hfs_fork_read`, is what makes a large volume countable — the same
reason `hfs_extents_read` exists for files.

Result on the 140 GiB volume formatted by `tools/disk-mode-format.sh`: the
bitmap's 4.6 MB is read through its runs, 36,594,065 free blocks are counted, the
header agrees, and the check is clean in about 0.2 s. Volume up to 275 GB at
4096-byte blocks are covered by the 8 MiB bitmap cap; beyond that the check says
it skipped rather than grinding.

Host coverage: a new case splits the allocation fork into two runs and checks the
count follows them (15 cases total).

## Leaf chains, key order and record bodies

The structural check now walks each metadata tree's leaf chain instead of trusting
its header. Three things are checked on every pass: the chain ends at the node
`lastLeafNode` names and holds exactly `leafRecords` records; catalog keys strictly
increase in leaf order, compared with the same `hfs_catalog_key_compare` the writer
uses, so FastUnicodeCompare decides the name order; and extents keys strictly
increase by fork type, file ID and start block, which for those fields is a raw
compare because every one of them is big-endian. Keeping the previous key across
the boundary is what makes the order check meaningful on a real tree; comparing
inside one node only would pass a tree whose leaves were shuffled.

Catalog record bodies are checked against the structure their type promises: 88
bytes for a folder, 248 for a file, a real ID in both, and for thread records the
two rules that catch a mis-built thread — the key names nothing and the body names
something. A record type outside 1–4 is a finding now; before, it was skipped
silently, which meant a catalog entry that no reader can resolve looked fine.

There are two traps in the byte layout, and both cost a false alarm before they
were understood. `HFSPlusCatalogFolder` and `HFSPlusCatalogFile` include their own
`recordType`, so a folder body is 88 bytes counting the type field, not 86 — the
first version flagged every folder on a real volume and counted zero of them. And
a thread record's key is its own CNID, not its parent's, so the first hand-built
clean catalog put its thread first and the order check correctly called it out;
the test data was wrong, not the check.

Host coverage is 22 cases now, including two clean catalogs (one folder, one file)
that must report nothing. Against real volumes: a 64 MB macOS `HFS+J` volume with
nested folders, 16 files and names such as `£ euro.txt` and `日本.txt` across a
128-node catalog is clean — that is the check that FastUnicodeCompare really is
the order macOS writes; the 32 MiB image is clean and the tampered one still
reports only its free-block mismatch; the 140 GiB volume is clean.

## Index nodes

The last level of the structural check is the one a search goes through first.
Every record in an index node is a key and a child pointer, and a search trusts
three things: the child exists, it is the level below (an index node until the
last step, a leaf after it), and the key that points at a subtree does not sort
after that subtree's first key. That last rule is the one worth stating
carefully. HFS+ leaves stale ancestor keys behind after a delete — an index key
may sit *below* the first key of its subtree and everything still works, because
the search only ever needs "not greater" — so the check allows a smaller key and
reports only a key that sorts above the subtree, which makes every record under
it unreachable.

The walk is iterative with a fixed stack of the tree's depth (the reader's own
limit is 32), pops a node, re-reads it per record because the child read lands in
the same scratch buffer, and pushes index children for the next level. A node
reached more often than the tree has nodes is a cycle and is reported as a chain
finding. The attributes tree is left out: no fixture here exercises its key
order, and guessing at it would be worse than saying so.

Host coverage is 26 cases, including a real depth-2 catalog — an index node over
two leaves — that must report clean, and three ways to break it: an index key
that sorts after its child's first key, a child pointer past the last node, and a
leaf that claims to be an index node. On the 64 MB macOS volume, whose catalog is
exactly that shape (depth 2, 128 nodes), the check is clean; the 140 GiB volume
and the 32 MiB image are unchanged.

## Where nothing is looking: coverage of the host suites

`tools/coverage.sh` builds every suite with clang's source-based coverage, runs
them, merges the profiles and reports how much of `firmware/` and `bootloader/`
the tests actually execute. At the time of writing: 16,126 lines, 13,254 hit,
82.2 %, and 2,872 lines no host test has ever run.

Two things had to be fixed before the numbers meant anything. `tests/firmware`
builds its objects with `HOSTCC`, not `CC`, so a coverage run that sets only `CC`
silently links uninstrumented objects and reports whole modules at zero — the
script now sets both. And the first aggregation dropped every `DA:` record with a
zero count, which made every file 100 %: a line with no hits is the point, so the
parser keeps it.

The map it produced is the useful part. The weakest files are the big writer
(`hfs_btree_tree.c`, 1549 lines, 76.6 %), libmad's `layer3.c` (81.7 %),
`flac_decoder.c` (81.0 %), `usb_msc.c` (77.0 %), the 6G USB HAL (76.9 %),
`hfs_catalog_write.c` (87.0 %), `layer12.c` (46.9 %), the bootloader's
`inner_image.c` (59.4 %), `disk_mode.c` (69.9 %) and `partition.c` (60.9 %).
Exactly one file is never executed at all: `bootloader/loader_error.c`, the
loader's `strerror` table.

## A random writer, and what it found

`tests/image/hfs_ops_test.c` runs a deterministic random sequence of create,
append, truncate, rename and delete against a disposable image, checks a model of
the expected catalog after every operation, and adds two checks the rest of the
suite does not have: every block a live file claims must be marked used in the
bitmap, and no block may belong to two files. The driver puts `hfs-check` and
`fsck_hfs` on top.

It found three bugs in the first hour, which is a fair measure of what
hand-written cases were missing.

**One: shrinking inside the last block failed.** `hfs_catalog_truncate_to` zeroed
the whole tail of the last kept block, from the new end to the block boundary,
even when the old size ended earlier in that block. The fork writer refuses a
range past EOF, so `truncate` to any size that stayed in the same block returned
`ARGUMENT`: "shave a few bytes off the end" simply did not work. The zero range
now stops at the old size, and `test_truncate_inside_last_block` covers the case.

**Two: clearing then rewriting an overflow record failed.** Truncating a file
whose fork has one overflow record clears that record and writes the smaller one
back in the same transaction. The clear emptied the extents tree; the set then
called delete again to make room, and the delete walked from a root node of zero
into the header node and returned `FORMAT`. `hfs_btree_delete` now asks the staged
header whether the transaction already emptied the tree and answers `NOT_FOUND`.

**Three: still open.** A longer soak — eight seeds, three hundred operations —
reproduces a fork whose block count outruns its extent records: seed 3,
operation 157, file `n22`, size 49152, 12 blocks claimed, 11 covered by inline
extents and no overflow record at logical 11. The append path is the suspect,
since no other operation touched that file between operation 135 and the failure.
The harness keeps the default run at two seeds so the target stays green while
this is chased, and `HFS_OPS_VERBOSE=1` prints every operation for the replay.

## One command, and a preview every night

**One command.** `tools/host-tests.sh` builds and runs the portable suites —
`hfsplus firmware bootloader vfs codec musicdb player ui usb` — with one
compiler, keeps a log per suite under `build/host-tests/`, and stops at the first
red one with its last twenty lines. `--sanitize` repeats the eight suites that
have a `sanitize` target under ASan and UBSan; `--macos` runs `tests/image`'s
seven disk-image drivers; `HOST_TESTS_IMAGE` adds `tests/library`, which needs a
volume. All three modes were green on this tree: 9 portable suites, 8 sanitizer
suites, 10 with `--macos` (the image suite takes 131 s, mostly `format-test`'s
150 GiB sparse image and `fsck_hfs`).

Writing the runner found one wrong assumption immediately: `tests/image`'s
`test` target runs `run-macos.sh`, so it is not portable and does not belong in
the Linux list. It is behind `--macos` now, and the Linux jobs never build it.

**CI.** `.github/workflows/tests.yml` runs on every push to `main` and every pull
request, in four jobs: the portable suites on ubuntu, the sanitizer pass, the
macOS disk-image suites on `macos-14`, and both firmware images
(`BOARD=6g image`, `DISKMODE=1 image`) with the distro `arm-none-eabi-`
toolchain. The Linux jobs exist because every host test so far was run on the
owner's Mac; the `--keep-going` flag exists so one run shows every red suite
instead of the first.

**Preview.** `.github/workflows/preview.yml` runs at 04:17 UTC and on dispatch.
It gates on the same host suites, builds both payloads with
`tools/preview-build.sh`, packs them and publishes `preview-YYYY-MM-DD` as a
GitHub prerelease. `README-PREVIEW.md` opens with what it is: preview code,
unproven, signed with a test key minted by that run, no supported install path.
A re-run replaces the day's release rather than failing on the tag.

The preview build uses the distro toolchain with `-Wno-error` on purpose. The
pinned Rockbox `arm-elf-eabi` 9.5.0 stays the build of record; a nightly that
fails on a warning a newer compiler invented would be noise, and a preview is not
a release artifact.

**Not attempted.** Neither workflow has run on GitHub — there is no run to
point at, and `docs/state.md` says so rather than calling them green. Nothing
here is a device run, and a preview release does not satisfy a single row of
`docs/validation.md`.
