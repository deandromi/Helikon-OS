## Both halves of Disk Mode have an image

**Goal.** A player can be formatted from a laptop with either the firmware or
the bootloader in charge.

**Firmware.** The Disk Mode image grew a confirmation gate — SELECT hands the
disk over, MENU or 30 s powers off — and a status line with the capacity and
the addressing mode. `helikon_board_storage_init_writable()` in the board gives
Disk Mode a writable block device; `helikon_board_storage_attach()` keeps the
read-only flag for everything else. `disk_mode` restore mode clears the
read-only flag on its private copy itself, and the host test now starts from a
read-only device so that clearing is what the write proves. Image: 40,524 bytes,
no `hfs_volume_probe` symbol.

**Bootloader.** `bootloader/hardware/helikon_usb_disk_hw.c` builds the seam the
firmware stack expects over `ata_read_sectors`/`ata_write_sectors`/`ata_flush`,
`udelay` and `PWRCON`, polls `helikon_usb_irq()` instead of reaching into the
donor VIC, asks for SELECT, and calls `helikon_disk_mode_start()` after
`storage_init()`, before any mount. The entry is `noreturn`, so no path can
fall through into the donor's filesystem code. `donor-usb-disk.patch` adds the
sources and the call; `tools/build-usb-disk-bootloader.sh` exports the donor at
the pinned commit, applies it and writes the image and a DFU file.

## The clock-gate inversion

Auditing the controller against the donor's `usb-s5l8702.c` turned up one
thing that a mock cannot see: PWRCON bits are power-*down* gates, so enabling a
clock clears the bit. `clock.c`, `pmu.c`, `buttons.c` and `ata.c` all do that;
both USB seams set the bit, which gates the OTG and PHY clocks off before the
core is touched. Fixed in `firmware/hal/6g/usb_target.c` and
`bootloader/hardware/helikon_usb_disk_hw.c`; the audit table and the fixed
values live in `usb-device-stack.md` §11. The Disk Mode image is 40,524 bytes
after the fix, the bootloader image 108,296 bytes (SHA-256 `de9b67e3…`).

## Fuzzing the transport (T-115)

`tests/usb/fuzz_msc` is deterministic: a fixed seed produces the same byte stream
on every host, so a failure reproduces from the printed seed. It drives the real
`usb_msc.c` over a sparse 4 TB fake disk and covers four cases — whole disk,
volume window, read-only device, I/O faults — 162,500 commands per run, and runs
under ASan/UBSan in `make -C tests/usb sanitize`.

What it checks: the CBW is either accepted or refused with `HELIKON_ERR_FORMAT`
and nothing else; the window never moves; no sector outside the window is read
or written; a read-only device takes zero writes; the CSW has the `USBS`
signature, echoes the tag, carries a status byte in range and a residue no
larger than the declared transfer; a failed command leaves a sense key; a device
error is never reported as success; eject only ever comes from START STOP UNIT,
and reading it consumes it.

What it found: a refused CBW used to be dropped silently, with no CSW and no
state, so the host waited out its transfer timeout before resetting the pipe.
`helikon_usb_msc_phase_error_csw()` now builds the 13-byte answer — `USBS`, the
tag echoed from the broken CBW, zero residue, `PHASE_ERROR` — and
`disk_mode.c` sends it before returning to idle. `test_disk_mode` pins that
sequence, including the re-armed CBW afterwards.

Sizes after the change: Disk Mode firmware 40,524 bytes; bootloader image
108,296 bytes, SHA-256 `de9b67e3…`; DFU 116,432 bytes, `e27d3b38…`; `_moveend`
20,736 bytes inside `MOVE_AREA`. Still no device run.

## Replay hardening for the journaled writer (T-018)

The replay contract in `hfsplus-write-engine.md` §10.5 says replay is idempotent
and that the journal is preserved on any replay failure. Both were asserted in
prose and untested in bytes; the crash matrix cut the *transaction*, never the
replay.

`tests/image/hfs_crash_test` gained two modes:

- `replay-twice SCENARIO` — recover the image, close it, open and recover again.
  The second pass must find a clean journal and the identical tree. This is what
  idempotency looks like from outside: a replay that is not idempotent shows up
  as a changed tree or a journal that never goes clean.
- `replay-cut SCENARIO N` — fail the nth write of the replay itself, leaving the
  image half-replayed on purpose. The next recovery must land on one of the two
  legal states (before or after the transaction) and never on a mixture.

`tests/image/run-crash-macos.sh` now runs `replay-twice` at every cut point and
the double fault on a sampled subset (`DOUBLE_CUTS`, `DOUBLE_SCENARIOS`), with
`fsck_hfs -fn` after each, and takes `SCENARIOS="create grow"` to narrow a run
while iterating.

Evidence from the run on this machine (macOS, a 16 MiB `HFS+J` image made by
`hdiutil`): `SCENARIOS="overwrite grow"` covered 118 cut points across the write,
flush and partial matrices — overwrite 21 + 4 + 21, grow 34 + 4 + 34 — and every
one recovered, was idempotent on a second recovery, and came out of
`fsck_hfs -fn` clean. The 16 replay double faults at the first four cut points of
each write matrix all converged on a legal state and were fsck-clean too. Exit 0,
zero failures. No device was involved and nothing was written outside the test's
own temporary images.

## A read-only structural check (T-020)

`firmware/hfs/hfs_check.c` is the first slice of the anti-corruption work: a
read-only pass that answers whether a volume's metadata agrees with itself. Block
size and count; every fork's extents against the volume; fork sizes against the
blocks they have; the allocation file against the block count; the free-block
count against the bitmap when the whole bitmap is inline; and the catalog,
extents and attributes B-tree headers through the reader's own validation.
Nothing is written and nothing is allocated.

Two design decisions came out of running it against real volumes:

- **The bitmap's padding bits are not a finding.** macOS leaves them zero on a
  freshly formatted volume, so an earlier version flagged every real volume whose
  block count is not a multiple of eight. That is exactly the false alarm a scrub
  must not have; the padding is now ignored and a host test pins it.
- **"Not checked" is not "broken".** A large volume keeps its bitmap in the
  extents overflow tree, which this pass does not chase. `skipped` is a separate
  field from `problems`, so a 140 GiB volume reports clean with a note instead of
  a failure.

Evidence: 13 host cases (`tests/hfsplus/test_check`), one corruption each, clean
volume zero findings. A real 32 MiB `HFS+J` volume: clean, exit 0. The same
volume with `free_blocks` bumped by five: the mismatch is reported, exit 1. A
140 GiB volume formatted by `tools/disk-mode-format.sh`: clean with the bitmap
marked not checked, exit 0. `tools/hfs-check.c` is the host CLI behind those
runs (`make -C tests/image hfs-check`).

### The catalog counts, and two conventions that only real volumes show

The first draft of the catalog walk counted records with a one-byte record type
and treated the root folder as a normal folder. Both are wrong, and both are the
kind of wrong that only shows up against a formatted volume: the record type is a
big-endian 16-bit field after `2 + keyLength`, and the root folder has a catalog
record of its own — parentID 1, named after the volume — that the header's folder
count excludes.

With both fixed, the walk agrees with the header on every volume tried: a 32 MiB
`HFS+J` image reads 2 files and 2 folders (the two journal files and two hidden
folders), the 140 GiB volume from the format test reads 5 and 3 across 14,208
catalog nodes. The numbers are printed by `hfs-check` now, so a future mismatch
can be read instead of guessed at.

## Overflow extents, and the large volume's bitmap

The structural check now reads the allocation file through a resolved extent map:
`hfs_extents_collect` supplies the inline extents plus the records from the
extents overflow tree, in logical order, and a small reader walks that map. The
map, not `hfs_fork_read`, is what makes a large volume countable — the same
reason `hfs_extents_read` exists for files.

Result on the 140 GiB volume formatted by `tools/disk-mode-format.sh`: the
bitmap's 4.6 MB is read through its runs, 36,594,065 free blocks are counted, the
header agrees, and the check is clean in about 0.2 s. Volume up to 275 GB at
4096-byte blocks are covered by the 8 MiB bitmap cap; beyond that the check says
it skipped rather than grinding.

Host coverage: a new case splits the allocation fork into two runs and checks the
count follows them (15 cases total).

## Leaf chains, key order and record bodies

The structural check now walks each metadata tree's leaf chain instead of trusting
its header. Three things are checked on every pass: the chain ends at the node
`lastLeafNode` names and holds exactly `leafRecords` records; catalog keys strictly
increase in leaf order, compared with the same `hfs_catalog_key_compare` the writer
uses, so FastUnicodeCompare decides the name order; and extents keys strictly
increase by fork type, file ID and start block, which for those fields is a raw
compare because every one of them is big-endian. Keeping the previous key across
the boundary is what makes the order check meaningful on a real tree; comparing
inside one node only would pass a tree whose leaves were shuffled.

Catalog record bodies are checked against the structure their type promises: 88
bytes for a folder, 248 for a file, a real ID in both, and for thread records the
two rules that catch a mis-built thread — the key names nothing and the body names
something. A record type outside 1–4 is a finding now; before, it was skipped
silently, which meant a catalog entry that no reader can resolve looked fine.

There are two traps in the byte layout, and both cost a false alarm before they
were understood. `HFSPlusCatalogFolder` and `HFSPlusCatalogFile` include their own
`recordType`, so a folder body is 88 bytes counting the type field, not 86 — the
first version flagged every folder on a real volume and counted zero of them. And
a thread record's key is its own CNID, not its parent's, so the first hand-built
clean catalog put its thread first and the order check correctly called it out;
the test data was wrong, not the check.

Host coverage is 22 cases now, including two clean catalogs (one folder, one file)
that must report nothing. Against real volumes: a 64 MB macOS `HFS+J` volume with
nested folders, 16 files and names such as `£ euro.txt` and `日本.txt` across a
128-node catalog is clean — that is the check that FastUnicodeCompare really is
the order macOS writes; the 32 MiB image is clean and the tampered one still
reports only its free-block mismatch; the 140 GiB volume is clean.

## Index nodes

The last level of the structural check is the one a search goes through first.
Every record in an index node is a key and a child pointer, and a search trusts
three things: the child exists, it is the level below (an index node until the
last step, a leaf after it), and the key that points at a subtree does not sort
after that subtree's first key. That last rule is the one worth stating
carefully. HFS+ leaves stale ancestor keys behind after a delete — an index key
may sit *below* the first key of its subtree and everything still works, because
the search only ever needs "not greater" — so the check allows a smaller key and
reports only a key that sorts above the subtree, which makes every record under
it unreachable.

The walk is iterative with a fixed stack of the tree's depth (the reader's own
limit is 32), pops a node, re-reads it per record because the child read lands in
the same scratch buffer, and pushes index children for the next level. A node
reached more often than the tree has nodes is a cycle and is reported as a chain
finding. The attributes tree is left out: no fixture here exercises its key
order, and guessing at it would be worse than saying so.

Host coverage is 26 cases, including a real depth-2 catalog — an index node over
two leaves — that must report clean, and three ways to break it: an index key
that sorts after its child's first key, a child pointer past the last node, and a
leaf that claims to be an index node. On the 64 MB macOS volume, whose catalog is
exactly that shape (depth 2, 128 nodes), the check is clean; the 140 GiB volume
and the 32 MiB image are unchanged.

## A random writer, and what it found

`tests/image/hfs_ops_test.c` runs a deterministic random sequence of create,
append, truncate, rename and delete against a disposable image, checks a model of
the expected catalog after every operation, and adds two checks the rest of the
suite does not have: every block a live file claims must be marked used in the
bitmap, and no block may belong to two files. The driver puts `hfs-check` and
`fsck_hfs` on top.

It found three bugs in the first hour, which is a fair measure of what
hand-written cases were missing.

**One: shrinking inside the last block failed.** `hfs_catalog_truncate_to` zeroed
the whole tail of the last kept block, from the new end to the block boundary,
even when the old size ended earlier in that block. The fork writer refuses a
range past EOF, so `truncate` to any size that stayed in the same block returned
`ARGUMENT`: "shave a few bytes off the end" simply did not work. The zero range
now stops at the old size, and `test_truncate_inside_last_block` covers the case.

**Two: clearing then rewriting an overflow record failed.** Truncating a file
whose fork has one overflow record clears that record and writes the smaller one
back in the same transaction. The clear emptied the extents tree; the set then
called delete again to make room, and the delete walked from a root node of zero
into the header node and returned `FORMAT`. `hfs_btree_delete` now asks the staged
header whether the transaction already emptied the tree and answers `NOT_FOUND`.

**Three: still open.** A longer soak — eight seeds, three hundred operations —
reproduces a fork whose block count outruns its extent records: seed 3,
operation 157, file `n22`, size 49152, 12 blocks claimed, 11 covered by inline
extents and no overflow record at logical 11. The append path is the suspect,
since no other operation touched that file between operation 135 and the failure.
The harness keeps the default run at two seeds so the target stays green while
this is chased, and `HFS_OPS_VERBOSE=1` prints every operation for the replay.

## What the first four CI runs found

The workflow ran on the pull request before anything merged. It took four runs
to get every job green, and each red one was a defect no host run on macOS could
have shown.

**Seven suites could not compile on Linux, for one reason.** `firmware/lib/error.h`
resolved to glibc's `<error.h>` — the GNU extension declaring `error()` and
`error_at_line()` — so every `HFS_*` and `HELIKON_*` name came out undeclared in
`hfs_volume.c`, `bounce.c`, `wav.c` and the rest. The suites put `firmware/lib`
on the include path with `-idirafter`, *after* the system directories, on
purpose: the freestanding `string.h` in that directory must not shadow libc's.
macOS has no `error.h`, so nothing was shadowed there and every suite was green;
on glibc the shadowing hit 70 includes across six suites. `endian.h` is the same
shape of problem — `<endian.h>` is glibc's htobe/le family — so both are now
`helikon_error.h` and `helikon_endian.h`, with the reason written at the top of
each. The include-path trick stays.

**`tests/ui` generated an assembler file only one platform understands.**
`fixture_blob.S` was written with `.section __TEXT,__const` and underscored
symbols, which is Mach-O. The rule now picks the section name and the symbol
prefix from `uname -s`, so the same Makefile links the HDB fixture on macOS and
on ELF.

**The boot-info parser compared a host address against a device map.**
`helikon_boot_info_parse()` required the image to end at or below `page_base`,
which is where the page sits. On the 6G that is the same address, so the check
means what it says. On a host it is wherever the linker put the array, and both
host tests compared a synthetic image at `0x08000000` against their own page
address. That passed on macOS, where a static array lands high, and failed on
the sanitizer job, which links `-no-pie` and puts it at `0x40xxxx` — below
`0x08001234`, so the parser rejected every page and fourteen checks failed at
once. `struct helikon_boot_info_expect` now carries `image_ceiling`, the address
the image must stay under; the firmware passes the page address it always did,
and the host tests pass the device ceiling they are modelling.

**Fixtures need three Python modules and macOS ships none of them.** `mutagen`
and Pillow build the HDB fixture (`tests/ui`, `tests/musicdb`); `cryptography`
is what the loader suite links. Ubuntu takes `python3-pil` and `python3-mutagen`
from apt; the macOS runner's `python3` is Homebrew's and refuses
`pip install --user` with "externally-managed-environment", so that job builds a
venv and puts it on PATH.

**Two jobs were cancelled before they ran.** The `macos-14` job stopped one
second after starting, twice, with no steps and no log. `macos-latest` runs, so
that is what the workflow asks for now.

All four jobs — portable on ubuntu, sanitizers, the macOS disk-image suites, and
both firmware builds — passed on the pull request. The firmware image grew by
12 bytes, to 80,020, because the expect struct has one more field.

## The soak's lost block: an extent that grew without its count

The randomized writer had been red for three sessions on one finding: seed 3,
operation 157, file `n22` claiming twelve blocks while its extents covered
eleven, with no overflow record at logical 11. The lost block was both a hole no
reader could reach and a block the bitmap kept allocated — the shape of silent
data loss.

**What the log did not say.** With `HFS_OPS_VERBOSE=1` the harness printed the
operation *after* the checks, so the failing step was the one line missing and
the last line shown was a `create` of an unrelated file. That is why it read as
"a create corrupted a file it never touched". The description now prints before
the checks, which put `append n22 offset 36864 length 12288` in front of the
failure on the next run.

**The bug.** Appending three blocks to a fork with seven inline extents (nine
blocks) allocated blocks at 219, 220 and X. `append_tail_extent()` has a fast
path for the case where the next block follows the last extent, and that path
incremented the extent's `count` without moving `inline_blocks` — the total the
*next* overflow record is keyed by. So when the third block arrived, the record
was written with key 10 instead of 11: one logical block early, covering a block
that was already inline, and leaving logical 11 uncovered. The `record_blocks`
counter had the same hole for the record path, so a full record that grew would
have pushed the following record's key off too.

**The fix** is those two counters, and the regression is
`test_append_extends_new_extent`: the bitmap is arranged so the three appended
blocks are 66, 67 and 69, which forces the same three paths, then the test reads
all twelve blocks back and compares them. Reverting the fix makes it fail.

**Evidence.** `run-ops-macos.sh 8 300` now passes — eight seeds, the structural
check and `fsck_hfs -fn` clean after each — and the default run is 4 seeds x 200
operations. `make -C tests/hfsplus test` is 19 cases, sanitizer-clean. No device
run; every image here is a disposable 16 MiB one.

## Fuzzing the parsers, with something to prove

`tools/fuzz.sh` now builds and runs five libFuzzer harnesses. The interesting
part is that each one carries an invariant, because a target that only proves
"does not crash" mostly proves the compiler works:

| Harness | What it asserts |
|---|---|
| `id3v2` | a non-zero tag size only comes from a buffer that starts with the header, and every text field is terminated inside its array |
| `vorbis` | comments stay terminated; the FLAC walker only accepts a buffer that starts with `fLaC` |
| `hdb` | every offset the reader reports is inside the file it was given |
| `manifest` | a short or corrupt page is refused and leaves the output untouched; an accepted image size is inside DRAM |
| `journal` | a journal whose checksum does not match is never reported clean, and a hostile but checksum-consistent journal may fail to replay but never writes outside the device |

Writing them found the first thing in the corpus: my own "truncated tag" seed had
a syncsafe length of 2048, not 16, and `helikon_id3v2_tag_size()` answered 2058
for a 14-byte buffer. That is correct — the function reports what the header
declares and the caller clamps — but the harness had asserted the wrong
invariant. A fuzz target that fails on correct behaviour is a bug in the target,
so it now asserts the property that matters instead.

**The Mac problem.** Xcode's clang ships no `libclang_rt.fuzzer`, so the guided
mode cannot link here; Ubuntu's clang can. `--replay` covers the gap: it builds
the same harness against `tools/fuzz-replay-main.c` with ASan and UBSan and runs
every committed corpus file through it. That mode reaches 64 % of `id3v2.c`'s
regions from the corpus alone, which is what makes it a test rather than a
formality. CI does both: replay, then 20 guided seconds per harness, uploading a
reproducer if anything falls over.

**Where a finding goes.** `tests/<suite>/fuzz/findings/` gets the file libFuzzer
wrote; it is copied into `corpus/<harness>/` and committed with the fix, so the
bug is a test from then on.

## What the fuzzers found in the first minute

The `hdb` harness came back red on its first guided run in CI: a 128-byte
database whose header claimed six megabytes. `hdb_open` validated every table
offset against the header's own `file_size` — and never against the real file,
because `struct hdb_io` had no way to tell it. Opening such a file succeeded and
then every read would fail, which is a poor way to learn the database is
truncated.

`struct hdb_io` now carries `size`: the caller that knows the file size fills it
in, and `hdb_open` refuses a file whose size disagrees with the header. The
embedded blob (`firmware/ui/music.c`) and the VFS adapter
(`hdb_vfs_io_init`) both fill it, and `make -C tests/library macos` still passes
end to end over a real HFS+ volume. The reproducer is committed as
`tests/musicdb/fuzz/corpus/hdb/header-claims-more-than-the-file`, so the shape
stays a test.

That is the whole argument for a corpus plus invariants: the target found a real
gap in a reader that already had host tests, and the fix is nine lines instead of
a mystery in the field.

## A test that could not fail, and a check that found three things

Two pieces of test infrastructure, each built because the thing before it was
only accidentally trustworthy.

**The property test.** `helikon_block_read_bytes`/`write_bytes` sit between every
caller and the sector device: they turn an offset and a length into aligned reads
and read-modify-write sequences. Hand-written cases pick three offsets and miss
the fourth. `tests/firmware/test_bounce_props.c` walks 4000 deterministic ranges
over a model disk — biased toward the first and last sector, zero length,
lengths that cross boundaries, and offsets past the end — and after every write
compares the *whole* disk against a snapshot, so a byte moved outside the range
is a failure rather than a coincidence. It caught an injected `chunk + 1` in
`write_aligned` on the first run and passes on the clean tree (4000 iterations,
856 refused ranges, 3140 refused without a scratch buffer, 3142 writes).

**The failure that did not fail.** While writing it, the failure lines printed
and `make` still reported `PASS`, because `tests/firmware/test_check.h` counts
failures and only `helikon_test_report()` turns that count into an exit status —
and the test had been written to `return 0` instead. A probe confirmed the binary
exited 0 with a recorded failure. The header now installs an `atexit` guard: a
process that ends with failures counted and no report prints them and calls
`_Exit(1)`. Every other suite either fails immediately (`tests/hfsplus`) or
reports; the audit for the same shape found no other file.

**`tools/static-analysis.sh`** runs `clang --analyze` over 74 firmware and
bootloader translation units: firmware freestanding with `-nostdinc`, the
bootloader hosted, libmad and the donor glue skipped. The important detail is
that the analyzer **exits 0 whether or not it finds something**, so the script
counts findings from each log and `--strict` takes the status from that. CI runs
it strict.

It found three things in code that already had tests:

- a dead store in `vfs.c`: a local initialised from the file position and
  overwritten before any read;
- `flac_decoder.c` guarded the predictor shift with `shift >= 31` for a field
  that is five signed bits, so the guard was one wider than the shift it
  protected against — now `shift < 0 || shift >= 32`, with a comment saying why;
- `usb_msc.c` divided by `msc->sector_size` inside the transfer loop. The check
  at init makes it unreachable, but the analyzer could not follow the field
  through the loop; reading it into a local once says the same thing and is the
  clearer code.

All three fixed, and the run is 74 units, 0 findings. The fourth test added here
covers `bootloader/loader_error.c`, the only file in the tree with no test at
all: every code from 0 down to `UNSUPPORTED` has a distinct message, none
contains a `%`, and the fallback is reached for values outside the enum.

## Apple's own catalog as the oracle

The comparator is a reimplementation of `FastUnicodeCompare`, and every test of
it so far compared it with our own expectations. There is no way to settle that
from the inside: the expectation is the same reading of the same tables twice.
But HFS+ does not *use* a comparator somewhere privately — it builds the
directory's B-tree in that order. So a volume macOS wrote contains Apple's answer,
in the only form that matters, and reading it back gives an ordering to compare
against.

`tests/image/run-unicode-order-macos.sh` makes one disposable 24 MiB journaled
image and asks macOS for two things:

- **A corpus of 47 names** under `/Order`, created in a shuffled order so the
  creation sequence cannot pass for the comparator's order: digits (`1`, `02`,
  `9`, `10` — HFS+ compares them as digits, so `10` sorts first), case pairs,
  punctuation, precomposed Latin, decomposed combining marks, marks that need
  canonical reordering (`x\u0308\u0301`), Greek, Cyrillic, Hebrew, Arabic,
  Devanagari, CJK, Hangul, kana, emoji, fullwidth forms, and both sides of the
  255-unit limit (`a` × 255 and `a` × 254 + `b`).
- **A small tree** under `/Tree` with a zero-length file, one byte, a whole
  block, a partial block, a 70,000-byte file and two levels of folders.

Then `unicode_order_host` — a new host tool, read-only, stdout for the answer and
stderr for diagnostics so a warning cannot pass for a result — lists the catalog
back (`list`), re-sorts the same names with our comparator (`sort`), normalizes
the requested names (`canon`), walks the tree as `path<TAB>kind<TAB>size`
(`tree`), and reads the big file through its extents (`read`).

The run: 47 names, catalog order identical to ours, canonical forms identical,
eight tree entries identical, 70,000 bytes hashing to what macOS wrote,
`fsck_hfs` clean. And the first thing checked was that it can fail: inverting the
comparison in `hfs_fast_unicode_compare` turned the ordering check red and
printed the pairs that disagreed. Reverted, green again.

Two mistakes of mine were caught by the tooling rather than by review while this
was built. The tree walk reused the loop's iteration result as the error from the
recursive call, so a plain "one entry" was read as a failure and `tree` failed on
the first folder; `list` was unaffected, which is why the ordering half passed
first. And a stale object from an earlier mutation experiment made a property
test look red once — the reason `tools/host-tests.sh` cleans each suite.

## The writer's half of the differential, and the encoder it needed

The differential had one direction: macOS wrote, we read. The other direction
needs our writer to produce a volume and macOS to judge it, and that needs
something the writer did not have — a way to turn a UTF-8 name into a catalog
key.

`hfs_utf8_to_utf16be()` is the exact inverse of the decoder that has been there
since the reader: overlong forms, surrogate halves, a NUL, anything past
U+10FFFF and a name over 255 units are refused, and it does not normalize, which
stays `hfs_unicode_normalize_name()`'s decision. Six tests cover round trips for
each length class, the surrogate pair, every rejection class, both limits, and
that a composed name and its decomposed form reach the same canonical key through
it.

`hfs_image_test IMAGE order NAMES_FILE` uses it to create `/Order` and one file
per line of a names file through `hfs_catalog_create_folder` and
`hfs_catalog_create_file`, one transaction each. The macOS driver then does three
things with that image: `fsck_hfs -fn` has to accept the tree, macOS has to read
all 47 names back as files, and — the interesting one — our catalog order has to
be *the order Apple's image produced for the same names*. Not a set comparison:
the insertion order of our B-tree against Apple's, for 47 names chosen to sit on
every edge of the comparator.

Both outer oracles were checked by breaking the comparator on purpose. With
`hfs_fast_unicode_compare` inverted, our writer built the catalog in reverse
(`Gamma, Beta, alpha` for three names) and `fsck_hfs` said `Keys out of order`
four times — Apple's own checker rejecting what our comparator told the writer to
do. Restored, the same run is clean and the order matches.

The firmware image did not change size: nothing in the firmware calls the encoder
yet, so the linker drops it. It is there for the write path that needs it, and
`tests/image` is where it is exercised against a real volume.

## Playlist import, parsed like an input rather than a file format

A playlist is a list of paths, so the only thing the importer has to be good at
is text — and text from a laptop, a download or a hand edit is a claim, not a
fact. `firmware/player/playlist.c` reads M3U, M3U8 and PLS and yields one entry
at a time: a 512-entry array of paths is not something a 6G should hold, and the
caller resolves each path to a library id and moves on.

The rules are in the header, because a rule that lives only in the code is a rule
that gets broken by the next person: LF and CRLF, a UTF-8 BOM skipped, lines
trimmed, `#EXTINF` giving the title and duration (fractional truncated, `-1`
means unknown) for the *next* path, every other `#` line ignored, paths as UTF-8
rather than percent-encoded, resolved against the playlist's own folder with `.`
dropped and `..` popped. An entry that escapes above the root, carries a control
character, or is not valid UTF-8 is refused and **counted** — a malformed line in
the middle of a list must not lose the rest of it, and the UI has to be able to
say "3 entries skipped" rather than quietly playing 47 of 50. An entry longer
than 512 bytes, or a file with more than 512 entries, is refused rather than
truncated. A NUL byte anywhere refuses the whole file at open, because stopping
at it would hide a corrupt playlist behind a short one.

PLS gets its own rule: entries are read by numeric index, one scan for `FileN`,
`TitleN`, `LengthN`, because writers disagree about whether the title comes
before or after its file line and about whether the indices are contiguous. A gap
is skipped; `Length=-1` is unknown.

Nine host test groups pin each of those, including the four-refusals case that
must still produce the good entry after them. The `playlist` fuzz harness states
its invariants as properties of the output rather than of the code: every path
absolute, terminated, no control character, never more entries than the cap, and
`next` never failing after `open` succeeded. Eight seeds, including a file with a
NUL and a `[playlist]` with a gap.

Then CI's guided run found the first real defect, in twelve seconds of fuzzing:
a single `File00000087161458=ten.mp3` line. The parser read the highest PLS index
and walked to it one number at a time — 87 million scans of a 54-byte buffer, and
libFuzzer's five-second timeout went off. The scan is bounded by the entry cap
now, because an index above 512 can only ever be an entry the playlist would have
dropped anyway, and the in-range entries still parse. The reproducer is
`tests/player/fuzz/corpus/playlist/pls-huge-index`, so the shape stays a test.

It also found one thing in the test suite rather than the parser: the
player suite compiled `firmware/lib/mem.c` without `-DHELIKON_HOST_TEST`, so
`mem.h` exported the standard `memcpy`/`memset` names, the linker bound them to
the freestanding shims, and clang's idiom recognition turned `helikon_memcpy`'s
byte loop into a call to `memcpy` — which called `helikon_memcpy` again. At `-O2`
that is a stack overflow; under ASan the recognition is inhibited and it passes.
The suite now builds with the flag and `-idirafter` for `firmware/lib`, which is
what the codec suite already had to do for the same reason.

Nothing in the firmware calls the importer yet, so the image size did not move.

## From a playlist file to a queue, in one pass over the catalog

Parsing a playlist is the easy half. The hard half is that an HDB track record
holds a *string offset* for its path and nothing points at a track by name, so
resolving a playlist means finding the track whose path equals an entry. Doing
that per entry against every track reads the catalog once per pair: 512 entries
times a few thousand tracks is a number of HFS+ reads you would feel on a device.

`firmware/library/library.c` builds an index once per mount instead: one pass over
the tracks, one FNV-1a hash each, into a fixed table of 1024 slots at a load
factor of one half — 8 bytes per slot, no allocation, and a probe is a hash plus
one path comparison to *confirm* rather than to trust the hash. `complete` says
whether every track was indexed, so a caller can refuse to answer instead of
reporting "not found" for a track that was never indexed.

`helikon_library_queue_from_playlist` is then the whole path from a file to a
queue: parse, resolve, replace the queue with the track indices **in playlist
order** — and count four different things, because they are four different
questions and collapsing them would hide all of them:

| Count | Means |
|---|---|
| `entries` | the parser produced this many entries |
| `added` | resolved and placed in the queue |
| `missing` | a well-formed entry with no track in the library |
| `refused` | the parser rejected the line (escape above the root, control character, …) |

A `_Static_assert` pins the one limit that has to agree: the queue must be able to
hold a whole playlist, or an entry would be dropped for a reason the UI could not
explain.

Comparison is byte-exact, and the header says why: HFS+ is case-insensitive, so a
playlist written on a laptop may spell a path with different case than the file
has. That entry is reported as missing rather than guessed at, because folding
case here would mean importing the filesystem's table into the library's business.

The test builds the playlist *out of the fixture's own track paths* rather than
hard-coding names, so it checks the index against the catalog rather than against
a string someone typed: all six fixture tracks resolve to their own index, three
paths land in the queue in the order the playlist listed them, an absent path is
counted missing and a `../` entry counted refused, building the index twice gives
the same answers, and an empty playlist empties the queue.

## The playlist that was never a file

`tests/library` had a catalog of six tracks and one audio file, and the two had
nothing to do with each other: the catalog named
`/Music/The Ember Set/Night Harbour/01 First Light.m4a` while the volume held
`/Music/first.mp3`. Every test passed, because nothing ever asked the catalog
where a file was. That is the drift a test is supposed to catch, so the image now
carries a real file at each of the six paths the fixture names, and the suite
walks the path a user takes:

```text
/Playlists/first.m3u -> VFS read -> playlist parser
   -> index over the VFS-backed catalog -> queue -> HDB track -> path
   -> VFS open -> codec -> player -> PCM
```

The playlist is written to be awkward on purpose: one entry relative through
`..`, one absolute, one the catalog does not have, one that escapes the root, and
a `#EXTINF` line for good measure. The expected queue is `5, 2, 0` — the reverse
of nothing in particular, so a queue that came out sorted or that dropped a `..`
fails. `4 entries -> 3 queued, 1 missing, 1 refused`, and then each of the three
plays from its own catalog path: the file is found by asking the catalog, not by
the test knowing where it is.

Two things about how it was checked, because a green test that cannot go red is
decoration. Changing the expected first id from 5 to 4 printed `FAIL the queue
follows the playlist order` and exited 1, so the order assertion has teeth. And
the suite turned out to run *nowhere* in CI: `tools/host-tests.sh` drives the
macOS image suites through `tests/image`, and `tests/image` had no target for the
library suite at all. It has one now (`library-test`, a delegation to the other
Makefile) and it is in `MACOS_TARGETS`, so the playlist path is checked on every
pull request instead of when someone remembers it locally.

## A time that cannot exist is not a rounding problem

Cue sheets are how one FLAC file becomes twelve tracks: `INDEX 01 03:30:00` says
the second track starts three minutes and thirty seconds in, in CD frames — 75 to
the second, a number that comes from the Red Book and not from any disk. Get the
conversion wrong and the track starts in the middle of the previous one, which is
the kind of bug a listener hears immediately and a test only catches if it is
written to.

So `firmware/player/cuesheet.c` refuses instead of guessing. `00:60:00` is not 61
seconds, it is a broken file; a `TRACK` before any `FILE` has offsets relative to
nothing; a track that never gets an `INDEX 01` has no start, and playing it from
frame zero would replay the album. Each of those is *counted* in `refused` and the
rest of the sheet still plays, the same bargain the playlist importer makes: one
hand-edited line should not cost the other eleven tracks.

Two details were worth getting right rather than merely working:

- **One refusal, not three.** Refusing a `TRACK` also orphans its `INDEX` lines.
  Counting those too reported one broken statement as three, so an `INDEX` with no
  current track is ignored: the `TRACK` that owns it is the thing that is wrong.
  The test that caught this was the duplicate-number case, which expected one
  refusal and got two.
- **A pregap cannot follow its own start.** `INDEX 00` is the silence *before*
  `INDEX 01`; a sheet that puts it after would have the track begin before the
  silence that precedes it. It is clamped to the start and counted, so the track
  still plays and the sheet still reports itself incomplete.

Strings point into the caller's buffer — a caller with the file in memory already
has them — and the header is explicit that a `\"` stays escaped, because
unescaping would need a copy per field. The 99-track cap comes from the disc, not
from the device: a cue sheet for a whole CD is 99 tracks and a hundredth cannot
exist.

The fuzz harness asserts the invariants rather than survival: starts never go
backwards, no pregap after its start, every track belongs to a file that exists,
`complete` is exactly `refused == 0`, and every returned pointer is inside the
buffer it came from. Eight seeds, one of them a NUL in the middle of the file.

## Seven modules, one object, and a slash that let an escape through

The storage path had every part and no owner. The VFS mounts, the catalog reads,
the index resolves, the queue orders, the adapter feeds the codec and the player
plays — each proven on its own, and none of them ever wired together. A call site
that wires seven modules by hand is a call site that gets the order wrong once and
ships silence, so `firmware/library/music_source.c` now owns the combination:
open a volume, play a playlist that lives on it, then walk the queue with
next/previous, closing and reopening the file each step. About 68 KiB of `.bss`,
no allocation, and the rules are in the header because they are the ones a player
cannot be vague about — one file at a time, a failed open leaves nothing playing,
the end of the queue stops instead of wrapping, repeat-one replays the same id.

The test found a bug in the first ten minutes, and it was not a typo. The
playlist's folder was computed as `/Playlists/` — with the trailing slash, which
looks like the polite thing to hand a path joiner. But the parser splits a base
into components, so the trailing slash created an empty component and `..` popped
*that* instead of `Playlists`. The consequences were quiet and wrong in both
directions: the relative entries resolved to `/Playlists/Music/...` and were
reported missing, and `../../escape.m4a` — an entry that must be refused for
escaping the root — resolved to `/Playlists/escape.m4a` and was *accepted* as a
missing track. The counts came back `5 entries -> 1 queued, 4 missing, 0 refused`
where the same playlist through the direct path gave `4 -> 3, 1, 1`, which is
exactly what a second test over the same data is for.

`playlist_base` now returns `/Playlists`, the counts match the direct path, and
the comment above the fix says why it stays that way.

What the phase asserts, in order: the index built once and complete; the playlist
starts track 5 with the catalog's own path and non-silent PCM; `next` moves to
track 2 and reopens the file; `next` to track 0; `next` at the end is `NOT_FOUND`
with playback stopped and the position unchanged; `previous` goes back; repeat-one
replays track 2 without moving; repeat-all walks to 0 and wraps to 5; a playlist
of one stale entry is `NOT_FOUND` with `added == 0` and nothing playing; a folder
is not a playlist; a missing path is missing; `play_track` works directly; a
too-small path buffer is `BUFFER`; a track id past the catalog is refused and
leaves nothing playing; `close` twice is safe; reopening rebuilds the index.

## The mount the firmware never had

Paint the layers and one was missing. Block device, partition map, HFS+ core,
VFS, catalog, index, queue, player — all there, each with a host test, and every
one of those tests reached the layer below through a plain file handle: `fread`
at an absolute offset into a `.dmg`. The firmware, at boot, mounted nothing. That
is exactly why the Music hub still plays the blob embedded in the binary.

`firmware/storage/mount.c` is that step: scan the partition map, try each
partition as HFS+ in map order and keep the first that mounts, mount it read-only
through the VFS with fixed scratches, then open `/.helikon/music.hdb` through the
mounted volume. Three choices carry the weight:

- **"It mounts" beats "it is partition 3".** A 6G disk has firmware partitions
  that are not HFS+; an index-based guess works on one disk and fails on the
  next.
- **A dirty journal is reported, not cleared.** The mount is read-only, so the
  flag costs nothing — and clearing it would be the silent bypass the invariants
  forbid.
- **The catalog is optional.** A volume without `/.helikon/music.hdb` is still a
  volume to read files from, so mounting and opening the catalog are two calls.

The test now goes in at the bottom rather than the middle: it presents the
disposable journaled image as a read-only 512-byte block device, mounts it through
the firmware's own path, checks the partition count and range and a clean journal,
opens the catalog, and then plays `/Playlists/first.m3u` through a music source
whose reads come out of the block device — the first time in this repository that
a decoded frame's bytes travelled the route the device will use. It printed
`PASS storage mount: block device -> partition -> HFS+ -> catalog, playlist
played` on the first run, which after the playlist-base bug was almost
disappointing.

## Ten lines, and the arithmetic inside them

With the mount in place, the last thing between the disk and it was a table of
four function pointers: `helikon_ata_read/write/flush/power` already have the
block-ops signatures, so `ata_block.c` can hand the driver over as-is rather than
write four wrappers that drift apart from it later. The read-only gate is the
part that has to be deliberate: the firmware is read-only, so the device is
presented read-only unless a caller asks otherwise, and the block layer refuses a
write before the driver sees it.

The code worth writing is the geometry. `helikon_ata_block_info` refuses a sector
size below 512 or not a power of two, a zero sector count, and a size-count
product that does not fit a 64-bit capacity. That last check is not theoretical:
it is the shape of the bug where a 1 TB card is described as 128 GiB and the
driver happily reads the first eighth of the disk as if it were the whole thing.

The test replaces the driver with counted stubs, which lets it prove the boring
things that matter: a write on a read-only device answers `READ_ONLY` *without*
calling the driver, an out-of-range read answers `ARGUMENT` before the driver,
and an in-range read increments the stub's counter — so the ops table really is
the driver and not a copy of something that looked similar.

## The hub was reading a clock that never ticks

The Music hub does not draw a top bar; it blits the launcher tile as its
masthead. That tile is the owner's artwork, and it carries a mockup `12:34` and a
full battery — which on the launcher is a picture of the product, and on a
firmware screen is a claim about hardware the HAL does not have: a monotonic
timer is not an RTC, and nothing in the firmware reads a fuel gauge. #62 removed

The pixel probe that should have caught it was pointed at x 150–200, which is

`mask_baked_hub_clock()` clears the tile's corner on the hub and

## The daily preview finally ran, and its own gate was broken

`preview.yml` had been committed for weeks and had never produced a release. The
first manual dispatch answered why in 43 seconds: the gate job installed `clang`
and nothing else, and `tests/musicdb` builds the HDB fixture with
`tools/hdb_build.py`, which imports Pillow and mutagen. `tests.yml` has installed
that pair since the fixtures moved into the Makefiles; this workflow was written
without it and nobody had run it to find out.

One step behind that was the same mistake in a different module:
`tools/make-firmware-image.py` signs the manifest with Ed25519 from
`cryptography`, which a bare ubuntu runner does not carry, so the build job would
have stopped at the signature even after the gate was repaired.

Both fixed as installs, then the workflow was dispatched again on `main`. It went
gate → build → publish and left `preview-2026-11-22` behind: a prerelease with
`payload-6g/`, `payload-6g-diskmode/`, both READMEs and a tarball. Downloading
that tarball and running `shasum -a 256` by hand showed the 6G image matching the
`SHA256SUMS` inside it (`3b842118…`), which is the only way to know the published
number is the number the build produced.

The images are 2,840 bytes larger than a local build with the pinned toolchain
(82,860 against 80,020) because the preview uses the distro `arm-none-eabi-`
compiler with `-Wno-error`. That is the documented trade: a preview is not a
release artifact and must not fail on a warning the toolchain of record does not
emit. The 04:17 UTC schedule has still not been observed; only the dispatch has.
