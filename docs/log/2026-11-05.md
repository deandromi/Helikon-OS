## Learned

- Rockbox on the Classic requires FAT32; HFS+ iPods are unsupported. This makes
  native HFS+ a real differentiator for Mac users, not only a technical choice.
- Rockbox’s Classic metadata budget is 1,800 bytes with a 500-byte item limit,
  and the Classic does not normalize metadata. A host-built normalized index is
  a credible improvement, but it needs a host/device parity test.
- Rockbox is far ahead in codec breadth, native plugins, the full WPS language,
  voice/languages and device coverage. A v1 feature-count race would fail; the
  project needs the finite parity set and explicit declines in D-29.
- The existing 25 goals already cover most of the differentiation. The missing
  piece was the competitor evidence, the install/update model, the codec/index
  policy and the release threshold.

## Rejected

- Matching every Rockbox codec, plugin, theme tag and device at v1. It conflicts
  with the lightweight, safety and sandbox goals; D-29 and C-11 record the
  tradeoff.
- A writable USB mass-storage LUN as the cross-platform write path. It bypasses
  the VFS/transaction engine; D-09/D-38 keep the read-only LUN plus a framed
  service mode.
- Adding FAT32 support to reach Rockbox’s install base. B-02 keeps native HFS+
  as the defining promise.

## Session 2 — audio-format parity (2026-11-05)

### Work

Reviewed the Rockbox iPod Classic manual Appendix B.1–B.2 and §7.21, the
Rockbox 2014 iPod Classic codec benchmark (`b320bba`, 2014-12-12, 216/54 MHz),
Apple’s 6G technical audio specification, the Rockbox `ipod6g.h` platform
limits and the Cirrus Logic CS42L55 codec metadata.

Added [`../audio-formats.md`](../audio-formats.md):

- all **37 audio format families (36 in Appendix B.1 plus Opus)**, with extensions, notes,
  measured decode cost and tier;
- the 6G platform ceiling: S5L8702 ARM926EJ-S at 216 MHz, 64 MiB RAM, 512 KiB
  codec buffer, CS42L55 24-bit/48 kHz-class codec;
- Tier 1 (eight families at v1), Tier 2 (full Rockbox audio parity at v1.x) and
  Tier 3 (beyond Rockbox, measurement-gated);
- decoder framework, workspace/clock rules, metadata/artwork policy,
  gapless/seek/resume rules, error taxonomy and the test corpus.

Revised D-34; added D-49 (decoder provenance/licensing), D-50 (output ceiling
and resampling) and D-51 (metadata/artwork/gapless). Added T-096–T-102
(all `planned`). Updated the roadmap, tasks, competitive matrix, validation,
FAQ, state, README, file-map, firmware architecture and design-paper appendix.

### Evidence

- Rockbox benchmark: iPod Classic `b320bba`, 2014-12-12, 216 MHz boosted and
  54 MHz unboosted; per-codec MHz and realtime percentages extracted.
- Rockbox `ipod6g.h`: `CPU_FREQ 216000000`, `CODEC_SIZE 0x80000`,
  `PLUGIN_BUFFER_SIZE 0x200000`.
- Apple iPod classic technical specifications: AAC, protected AAC, MP3,
  MP3 VBR, Audible 2/3/4, ALAC, WAV, AIFF.
- CS42L55 datasheet metadata: 24-bit stereo codec, 48 kHz-class conversion.
- No Helikon-OS decoder, host test or device run was produced. Every new task
  is `planned`; every new decision is `proposed`.

### Learned

- The 6G can decode most of the Rockbox set at 54 MHz; only AAC-HE/HEv2 and
  APE above `-c1000` need a boost or fail at 54 MHz.
- The codec is 24-bit and 48 kHz-class, but the exact 6G output path is not
  proven. Native 24/96 and native DSD are not supportable claims on the stock
  device.
- Rockbox’s FLAC high-res/multichannel downmix to 16-bit stereo is a real
  limitation Helikon-OS could beat if the 24-bit path measures clean.
- “At least all Rockbox audio formats” is 37 families (36 in Appendix B.1 plus
  Opus), not a small codec list; Tier 2 must be a hard v1.x requirement.

### Rejected

- Declaring chiptune/tracker formats out of scope. They are audio formats in
  Appendix B.1.3 and belong in Tier 2.
- Claiming native 24/96 or native DSD from the codec datasheet. The output path
  is unproven and the codec is 48 kHz-class.
- Treating the 2014 Rockbox benchmark as Helikon-OS evidence.

### Next

1. Owner reviews D-34 and D-49–D-51.
2. If accepted, start T-096 (corpus/provenance) and T-097 (codec framework).
3. T-098 (output ceiling) waits for the audio measurement rig.

### Open questions

- Does the 6G I2S/DAC path preserve 24-bit words without truncation?
- Is 24-bit/48 worth the resampler/CPU cost on this codec?
- Which APE profiles are “supported” versus “best effort”?
- Is WMA Lossless worth the licence/CPU cost?
- Which chiptune/tracker families are v1.x core versus an optional pack?
- Which decoders need an upstream library instead of a Rockbox port?

### Learned

- The existing competitive matrix already covered the big architecture, but
  missed ordinary daily-use breadth: file operations, keyboard, hotkeys,
  quick screen, shortcuts, display/startup settings, playlist queue details,
  bookmarking/auto-resume detail, voice/talk clips and settings `.cfg`.
- Rockbox’s explicit refusals are useful differentiators: read-only health

  path; the first-party utility set is the daily-use path.
- Adding native plugin ABI or video playback. Both remain explicit declines.
- Treating the manual audit as proof that every feature is implemented.

## Launcher input, Benguiat wordmark and faster handoff

The launcher was visible but did not respond. The clickwheel init accepted
`0x8000023a`, which is the `WHEELTX` command value, as a ready RX status. It
returned before the controller reported real buttons, so the poll loop never
saw SELECT or the wheel. `helikon_buttons_init` now accepts only
`0x8000001a`, and the bogus second status format was removed.

SELECT or PLAY now opens a labelled placeholder app screen; MENU or SELECT
returns to the launcher. The wordmark is rasterized from the owner-supplied
ITC Benguiat Medium face; the `.otf` is not committed.

The loader no longer shows the firmware confirmation screen or the
"Executing signed test payload..." screen and no longer waits 3 s on the
success path. It jumps immediately after verification. The loader image is
106,184 bytes, SHA-256 `7f13e7e5…`; the launcher image is 86,164 bytes,
SHA-256 `4b0671d8…`. Host preview and the ten firmware groups pass. No 6G run
of this build yet.

## Launcher wheel latch, DMA loader, boot trim

The wheel still did not move after the status-format fix. The donor's wheel
handler clears the pending `WHEELINT` bits before reading `WHEELRX`; the poll
read the status without clearing the latch, so it kept returning the last
latched value. `helikon_buttons_poll` now clears the latch first.

The loader returns to ATA DMA for the fast path (`LOADER_PIO=1` keeps the PIO
handoff variant), the donor's 400 ms boot button-hold wait is 50 ms, and the
launcher build skips the LCD stage-list paint. The loader splash now goes
straight to the home screen with no debug list between them.

Loader image: 106,184 bytes, SHA-256 `7f13e7e5…`. Launcher image: 86,164
bytes, SHA-256 `4b0671d8…`. Host preview and the ten firmware groups pass. No
6G run of this build yet.
